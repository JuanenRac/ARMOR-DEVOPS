# 署名付きパッケージ: マシンが何をインストールするかの決め方

マシンのメンテナンス用ヘルパー(`armor_maintenance_agent.py`)は、GitHub 上の各リポジトリのリリースから A.R.M.O.R. のプログラム(`server`、`studio`、`network`、`ai`、`voice`、`devops`)を更新します。何かを展開する前に、次の 3 点をこの順に確認します。

1. **ハッシュ:** パッケージの SHA-256 が `armor-<コンポーネント>-<バージョン>.tgz.sha256` の値と一致すること。途中で切れたダウンロードを検出できます。
2. **署名:** `armor-<コンポーネント>-<バージョン>.tgz.sig2` に、マニフェストの Ed25519 署名（64 バイト、128 桁の 16 進数）が入っています。

   `armor-fw/1|<コンポーネント>|package|<バージョン>|<sha256>`

   署名にはリリースの秘密鍵（ノードのファームウェアに署名するものと同じ鍵）を使います。ファームウェアイメージと同じマニフェストで、ボードの位置に `package` が入ります。ヘルパーは、コードに組み込まれた公開鍵（`PACKAGE_PUBLIC_KEY`）で検証し、鍵の交換中は 2 本目の鍵（下記）でも検証します。`.sig2` がない、または検証できないリリースは拒否され（`missing_signature`、`bad_signature`）、システムは変わりません。何も展開されず、何も再起動されません。
3. **アーカイブ:** 絶対パス、`..`、リンク、デバイスファイルは含まれないこと。

GitHub 上のリリースの内容しか変更できない人（アカウントの盗難、公開ツールの悪意ある依存パッケージなど）は、パッケージとそのハッシュは公開できても、署名は作れません。秘密鍵は GitHub に置かれないからです。マニフェストは署名をコンポーネントとバージョンに結び付けるため、過去の署名済みパッケージや別コンポーネントのものを最新として見せることはできず、ファームウェアイメージの署名（別のプロジェクト、実在のボード）がパッケージ署名として通ることもありません。従来の `.sig`（テキスト `armor-pkg/1|<コンポーネント>|<バージョン>|<sha256>`）だけでは足りなくなりました。以前に公開したパッケージに署名し直す間だけ、マシンの `armor.maint.env` に `ARMOR_MAINT_SIGNATURE=either` と書いた場合に限って受け付けます。

検証は純粋な Python(RFC 8032)で行われ、マシンに OpenSSL や追加モジュールは不要です。

## 公開する

```
python scripts/package_component.py server --repo ../ARMOR-SERVER --sign --publish
```

`.tgz`、`.sha256`、`.sig2`（マニフェスト）、`.sig`（従来のテキスト。未更新のヘルパーがまだ確認します）を書き出してアップロードします。署名ツールは `~/.armor/sign.mjs`（または `--signer` / `ARMOR_PACKAGE_SIGNER`）で、鍵は `ARMOR_FIRMWARE_KEY` か `~/.armor/firmware_ed25519.pem` から読みます。鍵がリポジトリにコピーされることはありません。署名ツールか鍵がないと `--sign` は失敗し、`--sign` なしでは両方あるときだけ署名します。ヘルパーが信頼する鍵以外は使われません。`--publish` は未署名のパッケージのアップロードを拒否します。

すでに公開済みのパッケージに署名するには、`.sha256` と一緒にダウンロードして次を実行します。

```
python scripts/package_component.py --sign-existing armor-server-0.5.7.tgz --upload
```

名前からコンポーネントとバージョンが決まります。`--upload` は、そのリポジトリのリリース `v<バージョン>` に `.sig2` と `.sig` を追加します（`gh` が必要）。

## GitHub Actions からの公開

このリポジトリのパッケージはワークフロー `package-build.yml`(手動で起動、`dry_run` は既定でオン)が作ります。`devops` パッケージのスクリプトを2つのランナーで2回パックし、2つが1バイトまで同一でなければ停止し、`armor-devops-<バージョン>.tgz` を `SHA256SUMS` と証明付きでアップロードします。鍵は持ちません。成功した実行のアーティファクトから、保守担当者のマシンで署名してリリースを公開するには:

```
gh attestation verify armor-devops-<version>.tgz --repo JuanenRac/ARMOR-DEVOPS
python scripts/package_component.py --sign-existing armor-devops-<version>.tgz --upload
```

リリースには保守ヘルパーが必要とする `armor-devops-<バージョン>.tgz`、`.sha256`、`.sig`、`.sig2` が含まれます。これらがないリリースでは、マシンは「このリポジトリにはリリースがない」と報告します。

## 緊急時の例外

署名なしでパッケージをインストールしなければならない場合(鍵を紛失したときなど)は、マシンの `armor.maint.env`(`$PREFIX/etc/` 内)に次の行を書き、終わったら削除してください。

```
ARMOR_MAINT_ALLOW_UNSIGNED=1
```

インストールのたびにこのファイルから読み込まれるため、HTTP API やプロセスの環境変数では設定できません。使用されるたびに、ヘルパーはジョブのログと自身のログに `WARNING` を書き、概要は `unsigned_allowed` を報告します。

## マシンの設定

署名に関する 2 つの設定は、何かをインストールするたびに `armor.maint.env` から読み込まれます（HTTP API やプロセスの環境からは読みません）。

```
ARMOR_MAINT_SIGNATURE=manifest
ARMOR_MAINT_NEXT_KEY=
```

`ARMOR_MAINT_SIGNATURE` は `manifest`（既定: `.sig2` だけが有効）か `either`（従来の `.sig` も有効）です。`ARMOR_MAINT_NEXT_KEY` は空か、鍵の交換中に組み込みの鍵に加えて信頼する 2 本目の公開鍵（64 桁の 16 進数）です。信頼する鍵は 2 本までです。ヘルパーの概要には `signature_mode` と `trusted_fingerprints`（各鍵の SHA-256 の先頭 16 桁。鍵そのものではありません）が表示され、マシンの管理者がどの鍵を信頼しているか確認できます。ここを変えることは、マシンが何をインストールするか決める方法を変えることなので、緊急用の例外と同様に、マシン上で root として行います。

## 鍵を変える

新しい鍵ペアを作ります。まず、新しい公開鍵を各マシンの `armor.maint.env` に `ARMOR_MAINT_NEXT_KEY` として書きます（または、**古い**鍵で署名し、`PACKAGE_PUBLIC_KEY` が新しい鍵になっている `devops` パッケージを公開します）。以後は新しい鍵でパッケージに署名します。その行がある間、マシンは両方の鍵を信頼します。すべてのマシンに新しい鍵が組み込まれたら、その行を削除します。ノードのファームウェアが信頼する鍵は 1 本（`fw_trust.hpp`）で、署名付きファームウェアのページの手順で変更します。

## テスト

`scripts/test_maintenance_agent.py` は、有効なマニフェスト署名、それがコンポーネント・バージョン・ハッシュに結び付くこと、ファームウェア署名・従来のテキスト・ハッシュ単体がマニフェストとして通らないこと、改ざんされたパッケージ、`.sig2` の欠落、別の鍵による署名、でたらめな文字列、従来の `.sig` のみ（拒否され、`either` のときだけ受理）、鍵交換の 2 本の鍵（3 本目は決して信頼されない）、例外（ファイルからのみ）、RFC 8032 のテストベクタ、ヘルパーの鍵が `fw_trust.hpp` のものと同じであることを確認します。使い捨ての鍵を使い、本物の鍵は使いません。

パッケージ作成ツールは古いビルドのパッケージ化を拒否します。`server` と `studio` では、`package.json`(Studio では `dist/version.json` も)のバージョンが `armor.project.json` と一致し、`dist/` がビルド元のソースより古くないことが必要です。先に再ビルドしてください(`npm run build`)。
